# Step 2 — Web as a BFF (one Postgres) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use `- [ ]`.

**Goal:** Web stops reading/writing the knowledge tables directly. Every knowledge operation
goes through a secret-authed engine endpoint. Keep a single Postgres — the tables stay
defined in Drizzle (migration source); web just no longer touches them. `chats`, `messages`,
`citations` (dashboard transcript) and the auth tables stay web-owned.

**Decision:** BFF boundary, ONE Postgres (no physical DB split). Spec:
`docs/superpowers/specs/2026-07-18-rearchitecture-domain-vs-delivery-design.md` (Step 2, minus
the DB split, per the 2026-07-18 scope decision).

## Global constraints
- No schema/migration changes. The knowledge tables remain in `web/lib/db/schema.ts`; only
  the engine reads/writes them at runtime after this step.
- Each slice is independently shippable and keeps the product working. Commit per slice.
- Engine endpoints are internal, `x-engine-secret`-authed, principal-aware.
- After the last slice, `web/lib/{documents,groups,source,telegram}.ts` import nothing from
  `@/lib/db/schema` for knowledge tables, and neither do the API routes/pages.
- Verify each slice: `npx tsc --noEmit` (web) + `uv run pytest -q` (engine, with DB).

## Engine endpoints to add (engine/app/main.py + helpers)
| Method · path | Replaces (web) |
|---|---|
| GET  `/documents` | `lib/documents.ts` list |
| GET  `/documents/{id}/groups` | `groups.ts::documentGroupIds` |
| POST `/documents/{id}/groups` | `groups.ts::setDocumentGroups` |
| GET  `/source/{chunk_id}` (principal-checked) | `lib/source.ts::getSource` |
| GET  `/groups` | `groups.ts::listGroups` |
| POST `/groups` | `/api/groups` POST (create) |
| PATCH/DELETE `/groups/{id}` | `/api/groups/[id]` |
| GET  `/groups/members` | `groups.ts::groupMemberUserIds` |
| POST `/groups/{id}/members` | `groups.ts::setGroupMembers` |
| GET  `/telegram/status` · `/telegram/links` | `telegram.ts::getTelegramStatus/listLinks` |
| POST `/telegram/links/{id}` (status + groups) | `/api/telegram-links/*` |
| (internal) `resolve_access(ws, user_id, role)` | `groups.ts::resolveAccess` → used by ask + source |

## Slices (each = a task, TDD where the engine gains logic)

### Slice 1 — Documents (read)
- Engine: `GET /documents?workspace_id=` → `[{id,filename,mime,bytes,status,error,created_at}]`.
  Add `engine/app/library/documents.py::list_documents(conn, ws)`; wire route in main.py.
- Web: replace `lib/documents.ts` body with a `fetch` to the engine (via `lib/engine.ts` helper
  `listDocuments(ws)`); `/api/documents` and `Sources.tsx` keep their shape.
- Test: engine DB-gated test that `list_documents` returns seeded docs scoped to the workspace.

### Slice 2 — Source viewer (read, permission-checked)
- Engine: `GET /source/{chunk_id}?workspace_id=&user_id=&role=` → `SourceView` or 404. Move the
  `getSource` permission logic (owner bypass / group intersect) into `engine/app/library/source.py`
  using the shared `resolve_access`. 
- Web: `lib/source.ts` calls the engine; `/s/[chunkId]/page.tsx` passes the principal.
- Test: engine DB-gated — restricted chunk returns 404 for a non-member, content for a member/owner.

### Slice 3 — Access resolution + groups
- Engine: `resolve_access(conn, ws, user_id, role)`; `answer_query` and `/source` use it.
  Endpoints: GET `/groups`, POST `/groups`, PATCH/DELETE `/groups/{id}`, GET `/groups/members`,
  POST `/groups/{id}/members`, GET/POST `/documents/{id}/groups`.
- Web: rewrite `lib/groups.ts` as thin engine clients; update `/api/groups*`,
  `/api/documents/[id]/groups`, `AccessManager.tsx`, and the `/api/ask` route (send `role`, not
  precomputed `group_ids`).
- Tests: engine `resolve_access` (owner→all_access; member→everyone+assigned); group set/read.

### Slice 4 — Telegram (read + link admin)
- Engine: GET `/telegram/status`, GET `/telegram/links`, POST `/telegram/links/{id}`
  (status and/or group assignment).
- Web: rewrite `lib/telegram.ts` reads to engine clients; update `/api/telegram-links/*`,
  `/api/integrations/telegram`, `Integrations.tsx`.
- Test: engine DB-gated — approve a link and assign a group; status reflects a connected bot.

### Slice 5 — Cleanup
- Delete now-dead Drizzle imports/queries from web knowledge libs; confirm
  `grep -rE "from '@/lib/db/schema'" web/lib/{documents,groups,source,telegram}.ts` is empty.
- Web `db` client is still used by auth + chat — keep it.
- CHANGELOG + a short note in CLAUDE.md that the engine owns all knowledge-table access.

## Success criteria
- `web/lib/{documents,groups,source,telegram}.ts` and the knowledge API routes contain no
  Drizzle queries against knowledge tables — only engine `fetch` calls.
- The access rule (`resolve_access`) exists once, in the engine, used by ask + source.
- Product works end to end (upload → ingest → ask → cited → source viewer; access groups;
  Telegram) with web never touching a knowledge table.
